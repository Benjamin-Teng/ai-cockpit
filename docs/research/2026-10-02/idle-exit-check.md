# idle-exit-check：`--exit-when-idle` 閒置自動結束驗收

desktop-launch-notify task 2.5 的驗收腳本（design D10）。真的啟動 `target/debug/cockpit.exe`，
用 Node 內建的 `WebSocket` 與 `fetch` 當客戶端，驗證 spec `desktop-launch`「閒置自動結束」的行為。
結尾輸出 `RESULT: PASS` 或 `RESULT: FAIL (N)`，失敗時結束碼非 0。

## 用法

在 repo 根執行，需先 `cargo build -p cockpit`：

```bash
node docs/research/2026-10-02/idle-exit-check.js
```

- 全程約 70 秒（四個情境依序跑，各自一個 cockpit 程序），不可與其他驗收腳本並行。
- 臨時設定放在 `os.tmpdir()`：監聽埠向系統要空閒 loopback 埠，runtime 指向不存在的 named pipe，
  不會碰 HERDR；cockpit 的工作目錄也在暫存目錄。
- 每個情境結束都依 PID 終止自己啟動的程序（`taskkill /PID`，不依映像名稱）並確認 PID 不存在，
  再刪暫存目錄；刪除失敗算 FAIL。

## 情境

「關閉」指客戶端 `close` 事件觸發的時間點 t0，近似後端「連線數降為 0」。

| 代號 | 步驟 | 斷言 | 對應 spec scenario |
|---|---|---|---|
| a | 連上 `/ws`、關閉 | t0 + 9 秒時仍在執行且尚未開始關閉；開始關閉於 t0 + 9～12 秒；程序結束且結束碼 0；結束不早於 t0 + 9 秒 | 最後一個畫面關閉後結束 |
| b | 連上、關閉，3 秒後重連（維持連線） | t0 + 15 秒時仍在執行、日誌沒有開始關閉 | 重新整理不會被誤殺 |
| c | 連上、關閉，8 秒時 `GET /api/state`（要回 200），12 秒時重連 | t0 + 11 秒（已過原本的 10 秒）仍在執行；t0 + 15 秒仍在執行、日誌沒有開始關閉 | 啟動器偵測延長期限 |
| d | 不帶 `--exit-when-idle`：連上、關閉，等 20 秒 | t0 + 20 秒仍在執行 | 沒有旗標時不結束 |

情境 c 的重連刻意放在 12 秒（GET 之後約 4 秒）：沒有 `GET /api/state` 延長期限的話，後端在 10 秒就會開始關閉，
11 秒時的斷言會失敗，所以這個情境確實能分辨「有無延長」。

## 時間容許

- **開始關閉的時間點**取自 cockpit 日誌中「開始正常關閉」那一行行首的 tracing 時間戳（UTC、微秒）。
  關閉流程在沒有 runtime 連線時只要幾毫秒，行出現與程序結束只差毫秒，輪詢檔案抓不到，所以讀時間戳。
  日誌文字或時間戳格式改了，腳本要跟著改（`cockpit/src/app.rs` 的 `shutdown_signal` 附近）。
- 斷言 a 的下限（9 秒）預留 1 秒給客戶端 close 事件與後端偵測連線結束的延遲；上限（12 秒）預留給排程抖動。
- 正式的關閉流程（`shutdown_all`）最多約 11 秒，所以「程序結束」的等待上限放寬到 t0 + 35 秒（9 秒前置 + 26 秒）；
  本腳本的 runtime 是不存在的 pipe，實際約在關閉後立即結束。
- 其餘情境的「仍在執行」斷言是在固定時間點檢查程序尚未結束且日誌沒有開始關閉，不依賴上限。

## 不在本腳本涵蓋

- **從未連線 60 秒**：時間太長、且時鐘可撥快，由 Rust 單元測試涵蓋（`cockpit/tests/idle_exit.rs`，以
  `tokio::time::pause` 驗 spec 五個 scenario，含此條）。
- 依 ledger 裁決，本腳本不要求在舊版跑紅：舊版不認得 `--exit-when-idle`，立即以參數錯誤結束，紅證明不了行為；
  行為由 task 2.1 的單元測試 red→green 把關。
